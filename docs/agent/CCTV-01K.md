# [Claude → Codex] CCTV-01K 네트워크 장애 흉내 시험

사용자가 승인했다. 지금까지의 측정은 모두 같은 PC 안의 mediamtx에서 받아 실제 네트워크의 지연, 지터, 패킷 손실을 겪지 않았다. 재현 가능한 방식으로 이 조건을 만들어 플러그인을 확인한다. CCTV-01J까지 끝난 최종 코드에서 진행한다. [CCTV-01C](CCTV-01C.md)의 절대 금지와 공존 규칙을 그대로 적용한다. 이미지 다운로드와 호스트 네트워크 설정 변경은 하지 않는다.

## 시험 환경

- 장애는 컨테이너 안에서만 건다. 호스트 네트워크와 Windows 설정은 바꾸지 않는다.
- 권장 구성: RHEL 8 이미지 컨테이너에서 Linux 패키지를 실행하고, 그 컨테이너의 네트워크 인터페이스에 `tc netem`을 건다. `tc`나 `NET_ADMIN` 권한이 없으면, 기존 로컬 이미지 중 `tc`가 있는 이미지로 중계 컨테이너를 만들어 mediamtx와 플레이어 사이에 둔다. 둘 다 불가능하면 ENV_BLOCKED로 기록하고 사유를 적는다.
- Windows 패키지 측정이 가능한 구성(예: 장애를 건 중계 컨테이너를 거쳐 Windows가 수신)이 있으면 함께 시험한다. 없으면 Linux 디코딩 범위만 판정한다.
- 각 조건에서 RTSP over TCP(기본)와 UDP를 모두 시험한다. 플러그인이 UDP를 지원하지 않으면 그 사실을 적는다.

## 재실행: tc 패키지 다운로드 승인 (2026-11-06 사용자 결정)

1차 실행은 로컬 이미지 36개에 사용 가능한 `tc`가 없어 28개 조합 모두 ENV_BLOCKED였다. 사용자가 **`tc` 패키지 다운로드를 승인**했다. 승인 범위는 다음과 같다.

- 대상: Rocky Linux 8 공식 저장소(`https://download.rockylinux.org/pub/rocky/8/BaseOS/x86_64/os/Packages/`)의 `iproute-tc`와 그 실행에 필요한 최소 의존 RPM(`iproute`, `libmnl`, `libbpf`, `elfutils-libelf` 등 실제 필요분). 전체 합계 50MB 이내.
- 방법: RPM 파일을 `C:\Users\ho270\AppData\Local\Temp\cctv\dl\rpm-tc\`에 내려받아 URL, 크기, SHA256을 기록하고, 서명 또는 체크섬을 확인한다. 기존 이미지는 바꾸지 않는다. 시험 컨테이너를 만들 때 RPM을 읽기 전용으로 마운트해 컨테이너 안에서만 `rpm -i`로 설치한다. 새 이미지를 만들거나 기존 이미지를 덮어쓰지 않는다.
- 컨테이너에는 `NET_ADMIN`만 추가한다. `--privileged`와 호스트 네트워크 모드는 쓰지 않는다. 호스트 PC와 WSL의 네트워크 설정은 바꾸지 않는다.
- Docker Desktop 커널에 `sch_netem`이 없어 `tc qdisc add ... netem`이 실패하면, 다른 다운로드로 우회하지 말고 근거를 남긴 뒤 ENV_BLOCKED로 끝낸다.
- 1차 실행에서 만든 제어기와 준비 검사(`b70ac92`, `ed1791c`)를 재사용하고, 1차 결과는 보존한다.
- 내려받은 RPM은 시험이 끝나도 최종 정리(CCTV-01Z) 전까지 남겨 둔다.

## 시험 조건

16채널 H.264 1080p30과 H.265 1080p30으로 각각 측정한다. 조건마다 120초 이상, 시작 10초는 제외한다.

| ID | 조건 | 의미 |
|---|---|---|
| N1 | 지연 50ms | 같은 사업장의 다른 망 |
| N2 | 지연 150ms, 지터 30ms | 원격지, VPN |
| N3 | 손실 0.5% | 품질이 낮은 스위치·무선 구간 |
| N4 | 손실 2% | 나쁜 회선 |
| N5 | 대역폭 제한(전체 스트림 합의 80%) | 회선 포화 |
| N6 | 10초 완전 단절 후 복구 | 네트워크 장비 재시작 |
| N7 | 지연 50ms + 손실 0.5% + 지터 10ms | 일반적인 원격 현장 |

## 판정

| 조건 | 기준 |
|---|---|
| N1, N2, N7 | 재연결 0, 디코딩 FPS ≥ 원본의 97%, 화면 정상. 지연은 추가한 네트워크 지연을 뺀 값으로 기존 기준 적용 |
| N3 | 재생 유지, 재연결 0. TCP에서는 손실이 재전송으로 흡수되는지 기록하고, UDP에서는 깨진 프레임 수와 회복 시간을 기록 |
| N4, N5 | 크래시와 멈춤 없이 재생 유지. 재연결이 생기면 자동 복구되고 반복되지 않음. 수치는 기록만(기준 미적용) |
| N6 | 단절 중 마지막 화면 유지, 복구 후 5초 안에 전 채널 재생, 크래시 없음 |
| 공통 | 메모리와 스레드가 조건 종료 후 원래 수준으로 돌아옴 |

N4와 N5는 정상 재생을 기대할 수 없는 조건이다. 플러그인이 견디는지(크래시, 무한 재연결, 메모리 증가가 없는지)만 본다.

## 미달 시 대응

- 크래시, 무한 재연결, 메모리 누적, 복구 실패는 결함으로 보고 원인을 찾아 고친다.
- 기준 미달이 설정값(읽기 시간 초과 5초, 재연결 간격, 패킷 큐 크기 등) 때문이면, 기본값을 바꾸지 말고 먼저 수치와 함께 권장 설정을 제안한다. 기본값 변경은 사용자 결정 뒤에 한다.
- 코드를 고치면 영향받는 기존 회귀(지연 4조건, 정지 시험, `package_win_16ch`, fault, 60분 soak)를 다시 실행한다.
