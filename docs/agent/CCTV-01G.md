# [Claude → Codex] CCTV-01G 코덱별 검증

사용자 질문: 다양한 코덱(특히 Linux)에서도 문제가 없는가. 지금까지 측정한 것은 H.264 8비트 4:2:0, B프레임 없음, 키프레임 1초 한 가지뿐이다. 사용자가 진행을 승인했다. [CCTV-01C](CCTV-01C.md)의 절대 금지, 다른 작업과의 공존, 직렬 측정 규칙을 그대로 적용한다. CCTV-01F 최종 코드에서 시작한다.

## 확인된 사실

- 포함된 FFmpeg(n8.1 LGPL, Windows 빌드에서 확인)에는 h264, hevc, mjpeg, mpeg4, vp9, av1 소프트웨어 디코더와 CUVID, D3D11VA, VAAPI 하드웨어 가속이 있다. Linux `.so`의 디코더 구성은 아직 확인하지 않았다.
- 플러그인은 NV12, I420(YUVJ420P 포함)만 그대로 올린다. 다른 형식(P010 10비트, 4:2:2 MJPEG 등)은 swscale로 NV12 변환을 거친다.
- 기본 설정은 하드웨어 디코딩 4채널, 나머지는 소프트웨어다.

## G1. 코덱 지원 확인

- Windows `.dll`과 Linux `.so` 각각에서 위 디코더와 hwaccel 구성을 확인한다(Linux는 RHEL 8 컨테이너 안에서).
- 하드웨어 경로별로 실제 하드웨어 디코딩이 되는지 확인한다: Windows CUDA, D3D11VA, Linux CUDA. H.265 10비트처럼 하드웨어 출력이 P010이 되는 경우의 처리 경로를 확인한다.

## G2. 시험 스트림

이 PC의 ffmpeg로 mediamtx에 송출한다. 기존 도구만 쓰고 다운로드하지 않는다. 각 스트림 사양(코덱, 프로파일, 해상도, FPS, GOP, B프레임, 픽셀 형식)은 `ffprobe`로 확인해 기록한다.

| ID | 코덱 | 조건 | CCTV에서의 의미 |
|---|---|---|---|
| C1 | H.264 High | 1080p30, B프레임 2, GOP 2초 | 일반 카메라 메인 |
| C2 | H.264 High | 1080p30, GOP 10초 이상 | H.264+ 스마트 코덱 |
| C3 | H.265 Main | 1080p30, GOP 2초 | 최근 카메라 대부분 |
| C4 | H.265 Main | 1080p60, GOP 2초 | 고프레임 카메라 |
| C5 | H.265 Main | 1080p30, GOP 10초 이상 | H.265+ 스마트 코덱 |
| C6 | H.265 Main10 | 1080p30 | 10비트 출력 카메라 |
| C7 | H.265 Main | 4K(3840×2160) 30 | 고해상도 메인 |
| C8 | MJPEG | 1080p30, 4:2:2 | 구형, 일부 엔코더 |
| C9 | H.265 메인 4K + H.264 서브 640×360 | 서브 스트림 전환 | 실제 운영 구성 |

B프레임은 NVENC 설정으로 넣고, 실제로 들어갔는지 `ffprobe`로 확인한다. 송출기 GPU 부하가 측정에 영향을 주지 않는지 확인하고, 영향이 있으면 미리 인코딩한 파일을 반복 송출한다.

## G3. 측정

각 스트림을 16채널로 80초 이상 측정한다. 시작 10초는 제외한다.

- Windows 패키지: 게임 60fps. 디코딩, 표시, frame age p95, 대체율, 손실, 재연결, 디코더 종류(채널별 HW와 SW), CPU, GPU 사용률, PNG.
- Linux 패키지(RHEL 8 컨테이너): `-nullrhi`로 소프트웨어 16채널과 CUDA 4 + 소프트웨어 12를 각각 측정한다. 렌더링은 ENV_BLOCKED이므로 디코딩만 판정한다.
- 서브 스트림 C9: 작은 크기에서 서브, 큰 크기에서 메인으로 자동 전환되는지 PNG와 CSV로 확인한다.

### 합격 기준

| 항목 | 기준 |
|---|---|
| 재생 | 16채널 모두 Playing, 손실·재연결·오류 0, PNG 정상(색, 비율, 깨짐 없음) |
| FPS | 디코딩과 표시가 원본 FPS의 97% 이상 |
| 지연 | frame age p95 ≤ 50ms(30fps 원본은 ≤ 70ms) |
| 대체율 | 1% 이하 |
| 긴 GOP | 첫 화면까지의 시간을 기록하고, 불필요한 재연결이나 소프트웨어 강제 전환이 없음 |
| 10비트, MJPEG | 색이 정상이고 위 기준을 만족 |

## G4. 미달 시 대응

- 기능 결함(색 오류, 깨짐, 재연결, 크래시)은 원인을 찾아 고친다.
- 성능 미달은 병목(디코딩, 변환, 업로드)을 CSV로 구분한 뒤 다음 순서로 검토한다.
  1. 변환 경로 최적화(예: P010을 GPU에서 처리, 다운스케일과 변환 결합).
  2. `MaxHardwareDecodeStreams` 기본값 조정. 4로 정한 근거(NVDEC 처리량)를 H.265에서 다시 측정한다.
  3. 서브 스트림 사용 권장.
- 이 PC(8코어 16스레드, RTX 4070 Ti)에서 하드웨어 한계로 기준을 넘지 못하는 조합은 수치와 병목을 기록하고, 운영 서버 사양에서의 예상과 권장 설정을 적는다. 기준은 낮추지 않는다.
- 코드를 고치면 CCTV-01F 최종 회귀 중 영향받는 항목을 다시 실행한다. 공용 C++라면 지연 4조건, 정지 시험, `package_win_16ch`, 60분 soak 포함이다.
