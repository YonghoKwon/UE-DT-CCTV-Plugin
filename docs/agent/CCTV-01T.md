# [Claude → Codex] CCTV-01T 지연 TCP 수신 개선 실험

사용자가 실험 추가를 승인했다. CCTV-01L이 끝난 뒤 실행한다. [CCTV-01C](CCTV-01C.md)의 절대 금지와 공존 규칙, CCTV-01K의 컨테이너 한정 netem 조건(승인 RPM 재사용, 새 다운로드 금지)을 그대로 적용한다.

## 배경 (CCTV-01K)

- 16채널 H.264 1080p30, 지연 50ms에서 TCP는 플러그인 13.2fps(재연결 3), UDP는 30.0fps였다. 손실 0.5~2%는 TCP도 30fps였다.
- 같은 50ms TCP 경로에서 UE 없이 FFmpeg 수신기 16개(스트림 복사)도 21~25fps로 떨어졌고, mediamtx가 "reader is too slow"로 프레임을 50회 버렸다. 1개 수신기는 30.7fps였다.
- 따라서 시험 경로(Docker 중계)의 TCP 처리량 한계가 크지만, 플러그인은 FFmpeg보다 더 낮았다. 플러그인 쪽 개선 여지를 확인한다.

## 실험

### T1. 원인 분해

- 같은 50ms TCP 경로에서 연결 수를 1, 4, 8, 16으로 바꿔 플러그인과 FFmpeg 수신기(복사, 디코딩 모두)를 비교한다. 플러그인 쪽 차이가 디코딩 부하 때문인지, 읽기 경로 때문인지 가른다.
- 플러그인의 읽기 스레드가 패킷 큐나 디코딩에 막혀 소켓 읽기가 늦어지는지 확인한다(패킷 큐 고수위, 읽기 대기 시간, 소켓 수신 큐 길이 `ss -tm`).
- 컨테이너 안 `net.core.rmem_max`, `net.ipv4.tcp_rmem`과 실제 소켓 수신 버퍼 크기를 기록한다. 호스트와 WSL 설정은 바꾸지 않는다. 컨테이너 네임스페이스의 sysctl 조정은 시험 컨테이너 안에서만, 실험 조건으로 명시해 허용한다.

### T2. 수신 버퍼 옵션

- `FDTCctvStreamConfig`(와 필요하면 프로젝트 설정)에 TCP 수신 버퍼 크기 옵션을 추가한다. 기본값 0은 지금 동작(FFmpeg 기본) 그대로다. FFmpeg RTSP/TCP에서 실제로 적용되는 옵션 이름(`buffer_size`, `recv_buffer_size` 등)을 소스로 확인해 쓴다.
- 0(기본), 1MB, 4MB로 같은 50ms·150ms 조건을 비교한다. 장애 없는 조건과 손실 조건에서 나빠지지 않는지도 확인한다.
- T1에서 읽기 스레드 막힘이 확인되면 그 원인도 고친다(예: 읽기와 디코딩 분리 강화). 고치면 영향받는 기존 회귀(지연 4조건, 정지 시험, `package_win_16ch`)를 다시 실행한다.
