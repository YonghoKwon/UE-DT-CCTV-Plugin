# [Claude → Codex] CCTV-01W 창 상태별 표시 FPS 진단

CCTV-01J 최종 회귀에서 Windows 16채널 일반 창 측정이 표시 48.5fps(대체율 19.1%)로 FAIL이었다. 같은 코드의 오프스크린 측정은 59.85fps로 PASS였고, CCTV-01G의 일반 창 60분 soak(잠금 화면 상태로 추정)는 59.9fps로 PASS였다. 디코딩은 60fps로 정상이었고 게임 프레임이 함께 떨어졌다. 사용자는 그 시간에 PC를 조작하지 않았다고 확인했다. 사용자가 PC 잠금을 해제한 상태로 유지한다.

[CCTV-01C](CCTV-01C.md)의 절대 금지와 공존 규칙을 그대로 적용한다. 시스템 전원 설정과 레지스트리는 바꾸지 않는다(진단용 프로세스 단위 설정만 허용, 끝나면 원래대로).

## 가설

1. 측정 창이 포그라운드가 아니어서 Windows 11 전원 제한(EcoQoS, 백그라운드 스로틀링)이 걸렸다.
2. 잠금이 풀려 창이 실제 모니터에 그려지면서 DWM 합성, 주사율 동기화, 창 가림이 영향을 줬다.
3. 같은 시간대의 화면 조작 준비(UI 자동화 도구)가 영향을 줬다.

## 측정

시작 전 `OpenInputDesktop`으로 잠금 해제 상태를 확인한다. 16채널 1080p60, 게임 60fps 제한, 1920×1080, 각 90초, 직렬로 실행한다. UI 자동화 도구는 측정 중 쓰지 않는다.

| ID | 조건 |
|---|---|
| W1 | 일반 창, 포그라운드(포커스 유지) |
| W2 | 일반 창, 다른 창 뒤(포커스 없음, 일부 가림) |
| W3 | 일반 창, 최소화 |
| W4 | 오프스크린(`-RenderOffScreen`) |
| W5 | W2와 같고, 진단용으로 해당 프로세스의 전원 제한만 끔(`SetProcessInformation`의 `ProcessPowerThrottling` 등) |

각 조건에서 표시·디코딩 FPS, frame age, 대체율, 게임 프레임 시간, 프로세스 CPU, GPU 사용률, 포그라운드 여부, 전원 제한 상태를 기록한다. 경계가 애매하면 같은 조건을 한 번 더 측정한다.

## 판단과 대응

- 원인을 근거와 함께 하나로 좁힌다. 좁히지 못하면 남은 후보와 이유를 적는다.
- 전원 제한이 원인이면: 플러그인이나 TestHost가 실행 중 해당 프로세스의 전원 제한을 끄는 방법(코드 또는 실행 옵션)의 장단점을 정리하고 사용자 결정을 받는다. 바로 기본 동작으로 넣지 않는다.
- 창 표시나 DWM이 원인이면: 운영 권장 실행 방법(예: Pixel Streaming 서버는 오프스크린, 전용 창 포그라운드 유지)을 정리한다.
- 01J의 `package_win_16ch` 일반 창 FAIL을 W1 조건으로 다시 측정해 판정을 갱신한다. 기준은 바꾸지 않는다.
- README에 운영 권장 사항을 적는다.
