# [Claude → Codex] CCTV-01J 테스트 프로젝트 RTSP 연결 점검 기능

사용자 요구: 실제 운영 프로젝트에 넣지 않고, CCTV 테스트 프로젝트(TestHost)를 실행해 RTSP 주소만 넣으면 연결이 잘 되는지, 문제가 없는지 확인할 수 있어야 한다. CCTV-01I까지 끝난 최종 코드에서 진행한다. [CCTV-01C](CCTV-01C.md)의 절대 금지와 공존 규칙을 그대로 적용한다.

## 원칙

- 기능은 `TestHost`에만 넣는다. 플러그인(`DTCctv`)의 공개 API는 바꾸지 않는다. 플러그인에 꼭 필요한 변경이 생기면 이유를 적고 최소로 한다.
- Blueprint 에셋 없이 C++(UMG `UUserWidget` 서브클래스나 Slate)로 만든다.
- 기존 측정 하네스(`-CctvUrl`, `-CctvCount` 등)는 그대로 동작해야 한다.

## 기능

### J0. 스트림 정보 로그 (플러그인, 사용자 추가 요청 2026-11-06)

사용자는 RTSP에 연결했을 때 카메라가 어떤 형식으로 송출하는지 로그로 확인하고 싶어 한다. 지금은 연결할 때 `코덱=h264 해상도=1920x1080 FPS=30.00 디코딩=cuda` 한 줄과 통계의 `CodecName`, `DecoderName`만 남는다. 이 예외로 플러그인을 고친다. 공개 API는 필드 추가만 하고 기존 필드는 바꾸지 않는다.

- **연결 직후 로그(1회):** 주소(계정 가림), 전송 방식(TCP/UDP), RTSP 서버 정보(SDP의 도구·세션 이름이 있으면), 비디오 트랙 수와 선택한 트랙, 코덱, 프로파일과 레벨(예: H.264 High 4.1, H.265 Main10), 해상도, 픽셀 형식과 비트 깊이, 크로마 형식(4:2:0, 4:2:2), 선언된 FPS, B프레임 여부, 오디오 트랙 유무와 코덱, 선택한 디코더(HW 종류 또는 SW)와 그 이유(예: HW 슬롯 초과, 미지원 코덱).
- **안정화 후 로그(재생 10초 뒤 1회):** 실제 측정값으로 확인되는 것. 실측 FPS, 평균 비트레이트, 키프레임 간격(GOP, 초와 프레임 수), B프레임 실제 사용 여부.
- **변경 로그:** 재연결이나 서브 스트림 전환으로 위 정보가 바뀌면 바뀐 항목만 한 줄로 남긴다.
- 위 정보를 `FDTCctvStreamInfo` 같은 BlueprintReadOnly 구조체로 스트림에서 조회할 수 있게 한다. 운영 위젯이 화면에 표시하는 데 쓸 수 있다.
- 로그 카테고리는 `LogDTCctv`, 레벨은 `Log`. 매 프레임 로그는 남기지 않는다.
- 단위 테스트: 프로파일 이름, 크로마와 비트 깊이 변환, GOP와 비트레이트 계산.
- CCTV-01G의 9개 스트림(C1~C9)에 연결해 로그가 실제 사양(`ffprobe` 결과)과 일치하는지 확인하고 결과에 붙인다.

J1의 점검 화면과 J2의 보고서는 이 정보를 그대로 사용한다.

### J0-1. DTCore 로그 연동 (플러그인, 사용자 요청 2026-11-06)

사용자 요구: 에디터에서 실행할 때는 지금처럼 UE 로그(`LogDTCctv`)를 보여 주고, 패키지에서는 DTCore가 관리하는 로그에 남긴다. 운영 프로젝트는 모두 DTCore 기반이다. CCTV 테스트 프로젝트(TestHost)에는 DTCore가 없고 필요 없다.

Claude가 확인한 사실(운영 프로젝트는 읽기만 했다):

- DTCore는 `m7at10_dt`, `ma0t10_dt`의 `Plugins/DTCore`에 있는 Runtime 모듈 `DTCore`다.
- 로그 API는 `UDxLogSubsystem`(GameInstanceSubsystem)의 `void WriteLog(const FString& LogContent, bool bPrintToScreen = false, FString LogFileName = TEXT(""))`다. 두 프로젝트에서 시그니처가 같다. `UFUNCTION`이 아니므로 리플렉션으로는 부를 수 없고, C++ 링크가 필요하다.
- `WriteLog`는 잠금을 건 버퍼에 쌓은 뒤 백그라운드 작업으로 날짜별 `DxLog_YYYY-MM-DD.log`에 쓴다. `bPrintToScreen=true`는 `GEngine` 화면 출력을 써서 게임 스레드 전용이다.

요구 사항:

- DTCore가 없는 프로젝트(TestHost 포함)에서도 플러그인이 그대로 빌드되고 동작해야 한다. DTCore를 필수 의존성으로 만들지 않는다.
  - 권장안: `DTCctv.Build.cs`가 대상 프로젝트에 DTCore 플러그인이 있는지 확인해, 있으면 `DTCore` 모듈 의존성과 `DTCCTV_WITH_DTCORE=1`을 넣고, 없으면 0으로 둔다. `.uplugin`에는 필요하면 DTCore를 선택적(`Optional`) 의존으로만 적는다. 더 나은 방법이 있으면 근거와 함께 제안한다.
- 로그 경로 선택:
  - 에디터 실행(PIE 포함): 지금처럼 `UE_LOG(LogDTCctv, ...)`만 남긴다.
  - 패키지 실행이면서 DTCore가 있을 때: `UDxLogSubsystem::WriteLog(..., false)`로 남긴다. UE 로그에도 남길지 설정으로 정할 수 있게 하고 기본값은 남김으로 한다.
  - DTCore가 없거나 서브시스템이 아직 없을 때(GameInstance 생성 전, 종료 후): UE 로그만 남긴다.
- 읽기·디코딩 스레드에서 호출해도 안전해야 한다. GameInstance와 서브시스템 수명을 약한 참조로 다루고, 종료 중 경쟁이 없게 한다.
- DTCore로 보내는 로그는 연결, 재연결, 상태 변경, 스트림 정보(J0), 오류만이다. 계정 정보는 가린다. 매 프레임 로그는 보내지 않는다.
- 이 PC에서 DTCore가 있는 상태를 시험하려면, 운영 프로젝트의 DTCore를 **읽기 전용으로 복사**해 시험 전용 임시 프로젝트를 만든다. 운영 프로젝트 폴더는 바꾸지 않는다. TestHost에는 DTCore를 넣지 않는다. 임시 프로젝트는 커밋하지 않고 끝나면 정리한다.
- 검증: TestHost(DTCore 없음) 빌드·패키징과 기존 측정 하나, 임시 DTCore 프로젝트의 에디터 실행(UE 로그만 확인)과 패키지 실행(`DxLog_*.log`에 CCTV 로그가 남는지 확인).
- README에 운영 프로젝트 적용 방법을 적는다.

### J1. 주소 입력과 재생 (Windows 패키지, 화면 있음)

- 실행하면 점검 화면이 뜬다. RTSP 주소를 한 줄씩 추가하고 삭제할 수 있다. 최대 16개.
- 각 주소에 서브 스트림 주소(선택)와 사용자 이름·비밀번호(선택)를 따로 넣을 수 있다. URL에 계정을 직접 넣는 형식도 받는다.
- 시작하면 격자로 재생한다. 창 크기와 격자 배치를 바꿀 수 있어 크기 변경 동작도 볼 수 있다.
- 각 채널에 상태를 겹쳐 표시한다: 상태(연결 중, 재생, 재연결), 코덱, 해상도, 원본 FPS, 디코딩·표시 FPS, 디코더(HW/SW), 재연결 횟수, 패킷 손실, 프레임 교체, frame age, 마지막 오류.

### J2. 자동 판정과 보고서

- 점검 시간(기본 60초, 변경 가능)이 지나면 채널별로 판정한다.
  - PASS: 시작 10초 이후 재생이 유지되고, 재연결·패킷 손실·디코딩 오류가 0이고, 표시 FPS가 원본의 97% 이상.
  - WARN: 재생은 되지만 위 조건 중 일부 미달(예: 소프트웨어 디코딩, 프레임 교체, 긴 GOP로 첫 화면까지 오래 걸림).
  - FAIL: 연결 실패, 인증 실패, 코덱 미지원, 재생 중단.
- FAIL과 WARN에는 원인을 사람이 읽을 수 있는 문장으로 적는다. 예: "인증 실패(401)", "포트 연결 시간 초과", "H.265 10비트를 소프트웨어로 디코딩 중".
- 결과를 화면에 표로 보여 주고, `Saved/CctvCheck/<시각>/`에 `report.md`, `report.json`, 채널별 CSV, 스크린샷을 저장한다.

### J3. 화면 없는 실행 (Linux 서버, 자동화)

- 같은 점검을 명령줄이나 설정 파일로 실행할 수 있다. 예: `-CctvCheckList=<파일>`, `-CctvCheckSeconds=60`. 결과 파일은 J2와 같다.
- 기존 `linux_server_check.sh`가 이 기능을 쓰도록 맞추거나, 함께 쓰는 방법을 README에 적는다.

### J4. 보안

- 비밀번호와 계정이 포함된 URL은 화면 표시, 로그, 보고서, 스크린샷 파일명 어디에도 평문으로 남기지 않는다(`DTCctvMaskUrlCredentials` 사용).
- 주소 목록 저장은 선택 기능으로 한다. 저장할 때 비밀번호는 기본적으로 저장하지 않는다. 비밀번호까지 저장하는 옵션을 둔다면 Windows는 DPAPI로 암호화하고, 저장 위치를 화면에 표시한다.
- 저장 파일은 저장소에 커밋되지 않도록 `.gitignore`를 확인한다.

### J5. 오프스크린 실행의 비정상 종료 원인 확인 (Claude 검수 추가)

CCTV-01G 회귀에서 `-RenderOffScreen` 실행 한 번이 0xC00000FD(스택 오버플로)로 비정상 종료했다. 시작 때 D3D12 스왑체인 ensure, 종료 때 Landscape 접근 검사 오류가 함께 남았다. 이후 측정은 일반 창으로 진행했다. 연결 점검 도구도 화면 없는 실행을 쓰므로 원인을 확인한다.

- 같은 조건(게임 30fps, 16채널, 오프스크린)으로 시작과 종료를 10회 반복해 재현율을 구한다. 플러그인을 끈 TestHost로도 같은 횟수를 돌려 비교한다.
- 크래시 덤프나 콜스택이 있으면 플러그인 프레임이 들어 있는지 확인한다.
- 플러그인이 원인이면 고친다. 엔진이나 TestHost 맵(Landscape) 문제면 근거와 함께 기록하고, 점검 도구가 영향을 받지 않는 실행 방법을 README에 적는다.

## 검증

- 단위 테스트: 판정 로직(PASS, WARN, FAIL 경계)과 계정 가림.
- 로컬 mediamtx로 정상 스트림, 잘못된 주소, 잘못된 포트, 인증 실패(mediamtx 인증 설정), 서버 중단, H.265 스트림을 넣어 각각 기대한 판정과 원인 문장이 나오는지 확인한다. 시험용 계정은 시험 중에만 쓰고 커밋하지 않는다.
- Windows 패키지에서 화면 조작(추가, 삭제, 시작, 크기 변경)을 실제로 하고 스크린샷으로 확인한다.
- Linux 패키지에서 화면 없는 점검을 실행한다.
- 기존 측정 하네스로 `package_win_16ch` 하나를 다시 돌려, 기존 동작이 깨지지 않았는지 확인한다.
