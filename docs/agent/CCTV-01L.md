# [Claude → Codex] CCTV-01L 최종 테스트: 코덱별 채널 수 한계

사용자 요청: 최종 테스트에서 코덱별로 몇 채널까지 괜찮은지 파악해 README에 적는다. CCTV-01K까지 끝난 최종 코드와 패키지로, 모든 작업의 마지막 측정 단계로 진행한다. [CCTV-01C](CCTV-01C.md)의 절대 금지와 공존 규칙을 그대로 적용한다. 측정만 하며 코드는 바꾸지 않는다. 측정 중 결함이 보이면 기록하고 Claude에게 보고한다.

## 측정 대상

CCTV-01G의 시험 스트림을 다시 쓴다(파일이 없으면 같은 사양으로 다시 만든다).

| ID | 스트림 |
|---|---|
| C1 | H.264 High 1080p30, B프레임 |
| C3 | H.265 Main 1080p30 |
| C4 | H.265 Main 1080p60 |
| C6 | H.265 Main10 1080p30 |
| C7 | H.265 Main 4K30 |
| C8 | MJPEG 4:2:2 1080p30 |
| H60 | H.264 1080p60(기존 기준 스트림) |

## 측정 방법

- 경로: Windows 패키지(게임 60fps, 화면 포함), Linux 패키지 SW(`-nullrhi`), Linux 기본 자동(CUDA 4 + SW).
- 채널 수: 4, 8, 12, 16에서 시작한다. 16에서 통과하면 20, 24, 32까지 올려 상한을 찾는다(플러그인 동시 연결 상한 설정이 있으면 그 안에서). 실패가 나오면 실패 직전 값과 실패 값 사이를 2채널 단위로 좁힌다.
- 각 측정은 80초 이상, 시작 10초 제외. 측정은 직렬로 하고, 한 조합당 1회로 하되 경계값은 2회 측정해 둘 다 통과해야 그 채널 수를 인정한다.
- 기준은 CCTV-01G와 같다: 전 채널 Playing, 손실·재연결·오류 0, 디코딩·표시 FPS가 원본의 97% 이상(채널별 최저값 기준), frame age p95 ≤ 50ms(30fps 원본은 ≤ 70ms), 대체율 1% 이하.
- 각 측정에서 CPU, GPU, NVDEC, 메모리 사용률을 함께 기록해 병목을 표시한다.
- 시간이 너무 길어지면(전체 4시간 초과 예상) 우선순위를 C3, C1, C7, H60, C4, C6, C8 순으로 두고, 남은 조합은 NOT_RUN과 이유를 적는다.

- 각 칸은 "기준을 만족한 최대 채널 수"다. 32에서도 통과하면 "32 이상"으로 적는다.
- 측정 PC 사양(CPU 8코어 16스레드, RTX 4070 Ti, 메모리)을 함께 적는다.
- CPU 코어 수와 GPU에 따른 대략적인 환산 방법, 채널을 늘리는 방법(`MaxHardwareDecodeStreams`, 서브 스트림, 카메라 설정)을 적는다.
- 이 PC 기준 값이며 운영 서버에서 01J 점검 도구로 다시 확인할 것을 적는다.
