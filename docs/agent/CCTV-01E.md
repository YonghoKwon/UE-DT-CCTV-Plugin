# [Claude → Codex] CCTV-01E 독립 검수 결함 수정과 최종 회귀

Claude가 CCTV-01D를 독립 검수한 결과다. 사용자 요청(모든 항목을 만족하도록 원인 파악과 수정)의 연장이다. [CCTV-01C](CCTV-01C.md)의 절대 금지, 다른 작업과의 공존, 직렬 측정 규칙을 그대로 적용한다. 합격 기준을 낮추지 않는다. 스레드 총수 기준은 사용자 결정 전까지 그대로 유지한다.

## 검수 결함

### E1. 8프레임 큐가 게임 FPS가 낮을 때 지연으로 고착됨 (코드 확인, 측정 없음)

`UDTCctvStream::RenderLatestFrame`은 틱마다 프레임 1개만 FIFO로 꺼낸다. CCTV-01D에서 `MaxPendingFrames`를 3에서 8로 늘렸다. 지금까지의 측정은 모두 `t.MaxFPS 144`, 게임 약 144fps라 큐가 바로 비워져 드러나지 않았다.

운영 프로젝트는 Pixel Streaming과 무거운 맵 때문에 게임 FPS가 60 이하일 수 있다. 코드상 예상되는 동작은 다음과 같다. 가설이므로 측정으로 확인한다.

- 게임 60fps, 영상 60fps: 한 번 쌓인 지연이 빠질 틈이 없어 최대 8프레임(약 133ms)에 머문다.
- 게임 30fps, 영상 60fps: 큐가 8장에 고정되어 약 267ms 지연이 계속되고, 프레임 절반이 교체된다.
- 16채널 전체 크기 표시에서 1080p NV12 8장씩이면 대기 프레임만 약 400MB다.

### E2. 운영 조건 FPS 미측정

`package_win_16ch`와 soak가 모두 게임 144fps 기준이다. 사용자 요구는 운영 환경의 60fps 이상이므로 게임 60fps 측정이 필요하다.

### E3. Close/Open 메모리 수렴 미확인

5회 반복 후 Private +45.9MiB, 스레드는 복귀, 핸들 +3이다. 5회로는 수렴과 누적을 구분할 수 없다. 위젯을 반복해서 여닫는 운영 패턴에 직접 영향을 준다.

### E4. 최종 코드에서 재실행하지 않은 게이트

Pixel Streaming 공존, drag, subset, substream 시나리오와 Linux 패키지 실행 일부가 이전 코드 결과다.

## 수행 순서

### 1. 지연 계측 추가

프레임별 디코딩 완료에서 렌더 명령 등록까지의 시간(frame age)을 세션 통계와 하네스 CSV에 추가한다. 채널별 평균, p95, 최대를 기록한다. 기존 지표의 이름과 집계는 바꾸지 않는다.

### 2. 수정 전 재현

현재 코드로 16채널을 80초씩 측정한다. 수치를 보존한다.

| 게임 FPS | 영상 | 비고 |
|---|---|---|
| 144 | 1080p60 | 기준 |
| 60 | 1080p60 | 운영 조건 |
| 30 | 1080p60 | 무거운 맵 조건 |
| 60 | 1080p30 | 일반 카메라 조건 |

게임 FPS 제한은 `t.MaxFPS`로 건다. 가설이 틀리면 근거를 적고 3단계를 조정한다.

### 3. 지연 상한 수정

짧은 지연의 프레임 보존과 지연 상한을 함께 만족시킨다. 판단 로직은 순수 함수로 분리해 단위 테스트한다.

방향(세부 구현은 Codex 판단):

- 틱에 프레임이 쌓여 있으면 짧은 버스트는 보존한다.
- 대기가 일정 시간을 넘게 이어지거나 frame age가 상한을 넘으면 오래된 프레임을 건너뛰어 따라잡는다. 건너뛴 프레임은 `FramesSuperseded`에 집계한다.
- 대기 프레임 메모리 상한을 유지한다.

합격 기준(16채널, 80초 이상, 시작 10초 제외):

| 조건 | 기준 |
|---|---|
| 게임 144, 영상 60 | 표시 ≥ 58, 대체 0, frame age p95 ≤ 34ms |
| 게임 60, 영상 60 | 디코딩 ≥ 58, 표시 ≥ 58, 손실·재연결 0, frame age p95 ≤ 50ms, 대체율 1% 이하 |
| 게임 30, 영상 60 | 표시 ≥ 28, frame age p95 ≤ 100ms, 손실·재연결 0. 대체는 불가피하므로 수치만 기록 |
| 게임 60, 영상 30 | 표시 ≥ 29, 대체 0, frame age p95 ≤ 50ms |
| 지연 회복 | 2초 정지 후 frame age가 기준으로 돌아오는 시간 ≤ 2초. 강제 정지를 하네스 옵션으로 넣어 측정 |

표시 프레임을 빨리 내보내기 위해 영상 재생 속도나 프레임 순서를 왜곡하지 않는다. 기준을 넘지 못하면 3회까지 수정하고, 그래도 미달이면 수치와 병목을 기록한다.

### 4. Close/Open 수렴 확인

16채널 Close/Open을 30회 반복한다. 각 재생 구간 끝에서 Private, 핸들, 스레드, GPU 메모리를 기록한다.

- 합격 기준: 마지막 10회의 Private 기울기가 회당 1MiB 이하, 핸들과 스레드가 늘지 않음, GPU 메모리가 늘지 않음.
- 넘으면 누수로 보고 원인을 찾아 고친다(`RetiredSessions`, 렌더 타깃, 스트림 객체, FFmpeg 문맥 해제 경로). 필요하면 강제 GC를 넣어 UObject 잔존과 구분한다.

### 5. 문서

- README에 `MaxReconnectDelaySeconds` 기본값 2초의 효과와 대가(꺼진 카메라에 약 2초 간격 재시도, 카메라 동시 연결 제한이 작으면 값을 늘릴 것)를 적는다.
- README와 DESIGN에 지연 상한 동작과 FPS 조건을 적는다.
- Linux Docker의 `NVIDIA_DRIVER_CAPABILITIES=all` 조건을 운영 점검 절차에 포함한다. 이미 있으면 확인만 한다.

### 6. 최종 회귀

C++를 확정한 뒤 다음을 직렬로 재실행한다. 이전 패키지 결과를 재사용하지 않는다.

- Editor 빌드, 전체 단위 테스트, Win64·Linux 패키징
- 3단계 표의 4개 조건과 지연 회복
- `package_win_16ch`, 1080p30 보조 측정
- Linux 소프트웨어 실행, Linux NVDEC, `linux_server_check.sh` 소프트웨어 모드
- Pixel Streaming 공존(Windows·Linux)
- 크기 변경 5개 시나리오(drag, extremes, subset, disconnected, substream). PNG 직접 검수
- fault, Close/Open 30회
- 마지막에 60분 soak를 **게임 60fps**로 실행한다. 표시 ≥ 58, 손실·재연결·오류 0, frame age p95 ≤ 50ms, 대체율 1% 이하, 메모리 추세를 판정한다.
- 같은 soak에서 스레드 모듈별 집계를 5분 간격으로 남긴다. 스레드 총수 일정 기준은 그대로 판정한다.

## 사용자 결정: soak 스레드 기준 변경 (2026-11-06)

사용자가 "총 스레드 수 일정" 대신 "플러그인·FFmpeg 스레드 일정, 총 스레드 수 증가 없음"으로 바꾸는 것을 승인했다. CCTV-01의 다른 합격 기준은 바꾸지 않는다. soak의 처음 10분은 제외하고 다음을 모두 만족해야 PASS다.

- 실행 파일, `ucrtbase`, NVIDIA 모듈(`nvcuda` 등)에서 시작한 스레드의 TID 집합이 일정하다. 이 집합이 플러그인과 FFmpeg 스레드를 포함한다.
- 변동은 OS 모듈(`ntdll` 등)에서 시작한 스레드에서만 나온다.
- 총 스레드 수가 늘지 않는다. 마지막 10분의 최댓값이 10~20분 구간의 최댓값을 넘지 않는다.
- 이전 기준의 결과(총수 min과 max)도 함께 기록한다.
