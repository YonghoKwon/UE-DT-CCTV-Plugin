# DTCctv 설계

## 목표와 합격 기준

| 항목 | 기준 |
|---|---|
| 플랫폼 | UE 5.3, Windows 패키징과 Linux(RHEL 8, glibc 2.28) 패키징 |
| 연결 유지 | 주기적 재연결 없음. 실제 장애 때만 자동 재연결 |
| 복구 시간 | 스트림 복구 후 5초 이내 재생 (키프레임 간격에 따라 변동) |
| 프레임 | 네트워크와 GPU가 정상이면 디코딩 손실 0. 화면에는 항상 최신 프레임 표시 |
| 채널 | 동시 16채널 |
| 크기 | UMG에서 자유롭게 변경. 표시 크기에 맞춰 출력 해상도 자동 조정 |
| 장시간 | 목표 72시간은 미검증. 60분은 재생·손실·재연결 조건 충족, 스레드 121~123 변동으로 FAIL |

카메라 재부팅이나 네트워크 단절 자체는 소프트웨어로 막을 수 없습니다. 이때는 마지막 텍스처를 유지하고 상태 이벤트를 보낸 뒤 자동으로 복구합니다. 재연결 문구·스피너 등 상태 표시는 운영 위젯의 책임입니다. `UDTCctvView`는 영상 표시만 담당합니다.

## 기존 FFMPEGMedia와의 차이

| 항목 | FFMPEGMedia | DTCctv |
|---|---|---|
| 재생 모델 | 파일 재생기(시계 동기화, 오디오, 자막, 탐색) | 실시간 최신 프레임 표시만 수행 |
| 장애 감지 | RTSP에서 동작하지 않음 | 읽기 기한과 출력 감시로 감지 |
| 색 변환 | CPU에서 BGRA로 변환 | NV12/I420 → RGB는 GPU 셰이더. 비지원 픽셀 형식 변환과 업로드 전 축소는 CPU |
| 스레드 | 채널당 약 5개 | 채널당 2개 (소프트웨어 디코딩 때는 FFmpeg 스레드 추가) |
| 설정 범위 | 전역 | 카메라별 |
| 닫기 | 호출 스레드에서 종료 대기 | 게임 스레드를 막지 않음 |

## 구조

```text
카메라
  │ RTSP (기본 TCP)
  ▼
읽기 스레드 ── 연결, 수신 기한 확인, 출력 감시, 재연결
  │ 패킷 큐 (상한 초과 시 다음 키프레임까지 건너뜀)
  ▼
디코딩 스레드 ── NVDEC → D3D11VA/VAAPI → 소프트웨어 순서로 선택
  │ 표시 대기 프레임 최대 3장 (NV12 또는 I420), 초과 시 오래된 것부터 대체
  ▼
게임 스레드 틱 ── 상태 이벤트, 렌더 명령 등록 (렌더 대기 중이면 건너뜀)
  ▼
렌더 스레드 ── 평면 텍스처 업로드 → YUV 셰이더 → 렌더 타깃
  ▼
UDTCctvView (UMG) 또는 머티리얼
```

## 모듈

| 모듈 | 역할 |
|---|---|
| `DTCctvRender` | 셰이더 경로 등록, YUV 셰이더, 평면 업로드. PostConfigInit에 로드 |
| `DTCctv` | RTSP 세션, 디코딩, `UDTCctvStream`, `UDTCctvSubsystem`, `UDTCctvView` |
| `DTCctvFFmpeg` | FFmpeg 헤더와 바이너리 (External) |

DTCore에는 의존하지 않습니다. 어떤 DT 프로젝트에도 그대로 넣을 수 있게 하기 위해서입니다.

## 핵심 결정

### 시계 동기화를 하지 않습니다
타임스탬프로 표시 시점을 맞추지 않습니다. 도착이 몰릴 때 최대 3장의 짧은 대기열에서 오래된 프레임부터 표시하고, 상한을 넘으면 오래된 것을 대체합니다. 시계 동기화로 지연을 누적하지 않으며 `FramesSuperseded`에 대체 수를 기록합니다.

### 장애 감지는 세 가지로 합니다
1. **수신 기한:** `av_read_frame` 전에 기한을 갱신하고, 인터럽트 콜백이 기한 초과를 확인합니다.
2. **출력 감시:** 첫 키프레임 패킷 전에는 30초 기다린 뒤 일반 재연결만 하며 소프트웨어 디코딩을 강제하지 않습니다. 키프레임 패킷을 받은 뒤 첫 출력이 없으면 그 수신 시점부터 `max(ReadTimeout, 10초)`를 적용하고 HW 세션은 소프트웨어로 재시도합니다. 재생 이후에는 마지막 출력부터 ReadTimeout을 적용합니다. 판단은 순수 함수 `DTCctvEvaluateOutputWatchdog`로 분리했습니다. 경계값 단위 테스트는 CCTV-01C에서 성공했으며 실제 카메라 시험은 남아 있습니다.
3. **읽기 오류:** `av_read_frame`의 오류를 그대로 재연결 조건으로 사용합니다.

### 재연결
연결이 일정 시간 유지되면 대기 시간을 초기화하고, 아니면 지수적으로 늘립니다. 동시에 복구할 때 몰리지 않도록 최대 25% 지터를 넣고, 동시 연결 시도 수도 제한합니다(기본 8개). 주기적인 재연결이나 시간 제한 종료는 플러그인에 넣지 않습니다. 시험 하네스의 실행 시간 제한과 Close/Open 반복은 TestHost 전용입니다.

### 과부하 처리
패킷 큐가 상한을 넘으면 큐를 비우고 다음 키프레임까지 건너뜁니다. 참조 프레임이 빠진 깨진 화면을 내보내지 않기 위해서입니다. 이때의 손실은 `PacketsDropped` 통계로 확인할 수 있습니다.

### 하드웨어 디코딩 V1은 시스템 메모리를 거칩니다
디코딩 결과를 시스템 메모리로 내려받아 업로드합니다. GPU 간 직접 공유는 D3D12와 Vulkan에 각각 별도 구현이 필요해 V1에서 제외했습니다. 하드웨어 장치 컨텍스트는 채널끼리 공유하며 기본 HW 슬롯 상한은 프로세스 내 4개, 나머지는 소프트웨어(채널당 FFmpeg 스레드 설정 2)입니다. 슬롯은 디코더 시도 전 예약하고 전체 후보 실패 또는 연결 정리에서 반환합니다. 증감은 코드 검토했으며 반복·장치 오류 시 실제 회수는 미검증입니다.

### 크기 조절
렌더 타깃은 표시 크기에 맞춰 줄어들고 원본보다 커지지 않습니다. 원본 변경은 즉시 반영하고, 표시 크기 10% 이상 변화는 0.25초 대기 후 반영합니다. 출력 폭·높이가 모두 원본의 절반 이하이면 디코딩 스레드에서 업로드 전에 축소합니다. 나머지 렌더 타깃 축소는 4탭 샘플링으로 보완합니다.

`SubUrl`을 지정하면 표시 폭이 기본 960px 미만인 상태 또는 그 이상인 상태가 2초 유지될 때 자동 전환합니다. 새 세션의 첫 프레임까지 기존 세션을 유지합니다. `SetUseSubStream` 호출은 해당 Open 수명 동안 수동 선택을 유지합니다. 전환 대기 중 새 주소가 실패하면 기존 영상과 새 세션의 장애 재연결을 유지하며 별도 전환 시간 제한은 두지 않습니다.

### 수명과 메타데이터

렌더 명령은 프레임·YUV 렌더러·진행 수 카운터의 공유 참조를 보관하며 `UDTCctvStream`을 캡처하지 않습니다. 텍스처의 render resource는 UE의 비동기 해제 fence로 보호됩니다. 실제 렌더 대기 중 GC와 반복 크기 변경은 별도 UE 검증이 필요합니다.

세션 닫기는 stop 신호·인터럽트·큐 Abort를 요청한 뒤 지연 해제 목록으로 넘깁니다. 읽기 스레드는 디코딩 스레드 종료 후 코덱·스케일러·입력을 정리합니다. 모듈 종료에서는 남은 세션을 기다린 뒤 공유 HW 장치와 FFmpeg 네트워크를 정리합니다. 읽기 스레드 생성 실패도 완료 상태로 남겨 회수할 수 있게 했습니다.

`CloseAllStreams`는 상태 콜백을 호출하기 전에 닫을 목록을 별도로 강하게 참조하고 관리 목록을 비웁니다. 콜백에서 목록을 바꾸거나 GC를 요청해도 순회 대상의 수명을 유지하며, 콜백이 새로 연 스트림을 기존 순회가 지우지 않게 합니다. 콜백 재진입의 실제 UE 검증은 남아 있습니다.

`UDTCctvView::Stop`은 월드 대신 스트림의 Outer인 서브시스템에서 스트림을 제거합니다. 스트림·소유자가 unreachable 또는 BeginDestroy/FinishDestroy 상태이면 닫기와 목록 수정을 건너뜁니다. Stop 없이 뷰만 제거하면 GC 전까지 재생이 계속될 수 있어 운영 위젯에서 명시적으로 Stop을 호출해야 합니다. 이 코드는 CCTV-01C에서 빌드했으며 실제 GC 경로 시험은 남아 있습니다.

CCTV-01A에서 원본·요청 해상도의 폭·높이를 한 잠금 아래 읽고 쓰도록 바꿨습니다. 각 표시 프레임에도 축소 전 원본 크기를 보관해, 다음 프레임의 해상도가 이전 프레임에 적용되지 않게 했습니다. 색 공간이 없는 HD 원본은 축소 후에도 원본 높이로 BT.709를 추정합니다. `sws_scale`의 출력 행 수가 목표 높이와 다르면 오류로 집계하고 프레임을 내보내지 않습니다. CCTV-01C에서 빌드와 FrameMetadata 단위 테스트가 성공했습니다.

### 패키징과 검증 상태

Linux UBT의 버전 접미사 링크 오류는 `INPUT(libavcodec.so.62)` 등 `.so` 텍스트 링커 스크립트로 우회합니다. 버전 바이너리는 바꾸지 않았으며 Windows DLL과 Linux SONAME 파일 5개씩을 실행 바이너리 옆으로 스테이징합니다.

2026-11-05 CCTV-01C에서 CCTV-01A·01B 수정 코드의 Windows Editor·Game 및 Linux Game 빌드와 양 플랫폼 Development 패키징이 성공했습니다. FrameMetadata·OutputWatchdog를 포함한 단위 테스트 7개 성공, 실패·미수행 0입니다. Windows SM5·Linux Vulkan SM5/SM6 전역 셰이더 캐시의 `FDTCctvYuvPS`와 Linux ELF의 버전 SONAME 참조도 확인했습니다. 이는 실제 패키지 재생 성능이나 장시간 안정성의 합격 증거는 아닙니다.

CCTV-01C에서 PixelStreaming 활성화, 연속/극단/일부 채널/단절 중 크기 변경, SubUrl 자동 선택, Close/Open 5회, 연속 PNG 및 채널별 CSV 시나리오를 실행했습니다. 준비한 PowerShell 실행기는 순차 실행과 소유 PID 확인을 사용하며, 시각 검수·자원 추세는 자동 PASS로 처리하지 않습니다. 기존 FFMPEGMedia와 함께 사용하지 않습니다.

`ps_coexist`의 기존 기준인 PixelStreaming 활성화 빌드의 시작과 16채널 재생은 유지합니다. 이 실행기가 판정하는 범위는 **"플러그인 로드 공존만 확인, 실제 스트리밍 동시 부하는 미검증"**이며, Windows·RHEL8 nullrhi 양쪽에서 마운트·16 Playing을 확인했습니다. 실제 클라이언트 연결·영상 수신이나 NVENC 인코딩과 RTSP 재생의 동시 부하는 시험하지 않습니다. 실행기 결과의 `known_limits`, `user_checks`와 각 PS 결과의 범위·미수행 상태에 명시합니다.

사용자 확인 항목은 Windows·Linux의 실제 시그널링·클라이언트 영상 수신, NVENC 인코딩 활성 증거, 그 상태에서 RTSP 16채널 재생의 FPS·손실·GPU 자원 추세입니다. 로드 공존 합격을 실제 스트리밍 동시 부하의 합격으로 사용하지 않습니다.

## 한계
- 화면 프레임레이트가 카메라보다 낮으면 일부 프레임은 표시되지 않습니다. 이 수는 `FramesSuperseded`로 집계합니다.
- 60fps 표시는 카메라가 60fps로 송출할 때만 가능합니다.
- 오디오는 지원하지 않습니다.
- `FramesDisplayed`는 렌더 명령 등록 수입니다. GPU 완료·모니터 표시를 직접 계측하지 않으며 `-nullrhi`에서는 증가시키지 않습니다.
- Windows 패키지 16채널 1080p60은 1920×1080 오프스크린에서 69.2초 평균 decode59.986/display59.986fps, 손실·재연결0으로 기준을 통과했습니다.
- RHEL8.10/glibc2.28 소프트웨어 RTSP 16 Playing, PS 로드 공존, 서버 복귀 후 4.908초 복구, 크기·서브 전환 PNG 표본과 Close/Open 5회를 확인했습니다. Vulkan은 VK_ERROR_INCOMPATIBLE_DRIVER로 실패해 렌더링 미검증입니다.
- 60분 소크는 3604.1초 평균 decode59.9992/display59.9991fps, 손실·재연결·디코딩 오류0입니다. 그러나 10~60분 threads121~123으로 일정 기준 FAIL입니다. Private +7.77MiB, 회귀+5.35MiB/h, 끝값기준+9.34MiB/h, GPU dedicated+0.039MiB이며 누수 여부는 확정하지 않았습니다.
- 극단 확대 순간 기존 저해상도 프레임의 일시적 흐림을 관측했고 후속0.5초 PNG에서 회복했습니다. 시각 검수는 PNG 표본 범위이며 모든 렌더 프레임을 보증하지 않습니다. 72시간·실제 Pixel Streaming 동시 인코딩 부하는 미검증입니다.
- 실제 카메라·현장·서버 수용 검증은 별도입니다. 현재 저장소의 결과를 현장 합격으로 취급하지 않습니다.
