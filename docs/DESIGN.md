# DTCctv 설계

## 목표와 합격 기준

| 항목 | 기준 |
|---|---|
| 플랫폼 | UE 5.3, Windows 패키징과 Linux(RHEL 8, glibc 2.28) 패키징 |
| 연결 유지 | 주기적 재연결 없음. 실제 장애 때만 자동 재연결 |
| 복구 시간 | 스트림 복구 후 5초 이내 재생 (키프레임 간격에 따라 변동) |
| 프레임 | 네트워크와 GPU가 정상이면 디코딩 손실 0. 화면에는 항상 최신 프레임 표시 |
| 채널 | 동시 16채널 |
| 크기 | UMG에서 자유롭게 변경. 표시 크기에 맞춰 출력 해상도 자동 조정 |
| 장시간 | 72시간은 미검증. CCTV-01E 게임60fps 60분은 표시59.935fps·p9535ms·대체0.106%·패킷/재연결/오류0, 승인된 스레드 기준 PASS. E4 원시 자원 비증가는 FAIL |

카메라 재부팅이나 네트워크 단절 자체는 소프트웨어로 막을 수 없습니다. 이때는 마지막 텍스처를 유지하고 상태 이벤트를 보낸 뒤 자동으로 복구합니다. 재연결 문구·스피너 등 상태 표시는 운영 위젯의 책임입니다. `UDTCctvView`는 영상 표시만 담당합니다.

## 기존 FFMPEGMedia와의 차이

| 항목 | FFMPEGMedia | DTCctv |
|---|---|---|
| 재생 모델 | 파일 재생기(시계 동기화, 오디오, 자막, 탐색) | 실시간 최신 프레임 표시만 수행 |
| 장애 감지 | RTSP에서 동작하지 않음 | 읽기 기한과 출력 감시로 감지 |
| 색 변환 | CPU에서 BGRA로 변환 | NV12/I420 → RGB는 GPU 셰이더. 비지원 픽셀 형식 변환과 업로드 전 축소는 CPU |
| 스레드 | 채널당 약 5개 | 채널당 2개 (소프트웨어 디코딩 때는 FFmpeg 스레드 추가) |
| 설정 범위 | 전역 | 카메라별 |
| 닫기 | 호출 스레드에서 종료 대기 | 게임 스레드를 막지 않음 |

## 구조

```text
카메라
  │ RTSP (기본 TCP)
  ▼
읽기 스레드 ── 연결, 수신 기한 확인, 출력 감시, 재연결
  │ 패킷 큐 (상한 초과 시 다음 키프레임까지 건너뜀)
  ▼
디코딩 스레드 ── NVDEC → D3D11VA/VAAPI → 소프트웨어 순서로 선택
  │ 표시 대기 프레임 최대 8장 (NV12 또는 I420), 초과 시 오래된 것부터 대체
  ▼
게임 스레드 틱 ── 상태 이벤트, 렌더 명령 등록 (렌더 대기 중이면 건너뜀)
  ▼
렌더 스레드 ── 평면 텍스처 업로드 → YUV 셰이더 → 렌더 타깃
  ▼
UDTCctvView (UMG) 또는 머티리얼
```

## 모듈

| 모듈 | 역할 |
|---|---|
| `DTCctvRender` | 셰이더 경로 등록, YUV 셰이더, 평면 업로드. PostConfigInit에 로드 |
| `DTCctv` | RTSP 세션, 디코딩, `UDTCctvStream`, `UDTCctvSubsystem`, `UDTCctvView` |
| `DTCctvFFmpeg` | FFmpeg 헤더와 바이너리 (External) |

DTCore에는 의존하지 않습니다. 어떤 DT 프로젝트에도 그대로 넣을 수 있게 하기 위해서입니다.

## 핵심 결정

### 시계 동기화를 하지 않습니다
타임스탬프로 표시 시점을 맞추지 않습니다. 도착이 몰릴 때 최대 8장의 유한 대기열에서 오래된 프레임부터 표시하고, 상한을 넘으면 오래된 것을 대체합니다. `FramesSuperseded`에 대체 수를 기록합니다. CCTV-01C의 max_frame48.6/62.7ms 지연과 프레임 대체4건을 근거로 CCTV-01D에서 3→8장으로 늘렸습니다. 압축 패킷 큐와 구분해 `QueuedFrames`, `PeakQueuedFrames`, `RenderCommandsInFlight`를 제공합니다. 8장 FIFO 보존과 9장 입력 시 대체1건을 단위 테스트로 확인했고, 최종60분 고수위4·대체0입니다. 장시간 표시 지연 시에는 여전히 오래된 프레임을 버립니다.

### 장애 감지는 세 가지로 합니다
이 절의 출력 감시와 별도로, CCTV-01E는 표시 대기 시간에 상한 정책을 적용합니다. 최대8장 FIFO의 큐가 비지 않는 상태가100ms 이상 지속되거나 선두 frame age가100ms를 넘으면40ms 안쪽으로 따라잡고 마지막 사용 가능한 프레임은 남깁니다. `DTCctvChooseStaleFrameSkip`을 순수 함수로 테스트하며, 건너뛴 수는 기존 `FramesSuperseded`에 더합니다. 짧은 버스트의 순서·재생 속도는 보존합니다.

frame age는 디코더 반환 직후부터 HW 다운로드·CPU 변환·대기열을 거쳐 렌더 명령을 등록할 때까지입니다. 채널별 전수1ms 히스토그램 상한 p95와 실제 평균·최댓값을 기록합니다. 네트워크 지연과 GPU 완료는 이 범위 밖입니다. 대기열8장 상한과 AVBuffer 참조 크기를 계측하고, 이미 알고 있는 표시 크기를 세션 시작 전에 전달해 첫 출력부터 원본 비율에 맞춰 축소합니다.

소비 속도가 입력보다25% 이상 빠르면750ms까지 버스트를 보존할 수 있습니다. 꽉 찬 대기열에서는 디코딩 작업 스레드가 공간 이벤트를 기다리고, 압축 패킷은 기존120개 큐에 남습니다. 게임 스레드는 기다리지 않으며 한 틱에1개씩 순서대로 꺼냅니다. 잘못된 속도 추정이나 지속 지연은 유예 만료 뒤 기존40ms 따라잡기로 처리합니다. 대기는 정지 신호로 즉시 깨웁니다. 대기 프레임은8장과24MiB 예산 중 작은 쪽으로 제한하고, 예산보다 큰 단일 프레임은1장만 유지합니다. 기존 대체 카운터를 유지하며14개 단위 시험에 생산·소비 동시성과 바이트 예산을 포함했습니다.

CCTV-01F의 역압 판단은 순수 함수 `DTCctvShouldBackpressure`로 소비자 호출350ms·실제 소비750ms·현재 프레임 대기750ms를 함께 확인합니다. GT 정지로 호출이 끊기거나 렌더 상한에서 소비 불가를 알리면 디코딩 스레드가 대기에서 빠져나와 오래된 출력 프레임을 대체합니다. 읽기 스레드의 패킷 큐가 넘쳐 GOP를 다시 기다리는 경로로 이동하지 않도록 한 방어입니다. 경계와 정상 버스트·소비 전·정체·시각 역행을 포함해15개 단위 시험을 실행했습니다.

16채널, 워밍업10초 제외80초 이상 기준은 게임144/영상60에서 표시58·p95≤34ms·대체0, 게임60/영상60에서 decode/display58·p95≤50ms·대체율≤1%, 게임30/영상60에서 표시28·p95≤100ms, 게임60/영상30에서 표시29·p95≤50ms·대체0입니다. 패킷 손실·재연결은0으로 판정합니다. 게임 틱2초 정지 후 새 제출 지연의 회복 상한은2초입니다. 최종 회귀와60분 소크는 별도 결과로 남깁니다.

1. **수신 기한:** `av_read_frame` 전에 기한을 갱신하고, 인터럽트 콜백이 기한 초과를 확인합니다.
2. **출력 감시:** 첫 키프레임 패킷 전에는 30초 기다린 뒤 일반 재연결만 하며 소프트웨어 디코딩을 강제하지 않습니다. 키프레임 패킷을 받은 뒤 첫 출력이 없으면 그 수신 시점부터 `max(ReadTimeout, 10초)`를 적용하고 HW 세션은 소프트웨어로 재시도합니다. 재생 이후에는 마지막 출력부터 ReadTimeout을 적용합니다. 판단은 순수 함수 `DTCctvEvaluateOutputWatchdog`로 분리했습니다. 경계값 단위 테스트는 CCTV-01C에서 성공했으며 실제 카메라 시험은 남아 있습니다.
3. **읽기 오류:** `av_read_frame`의 오류를 그대로 재연결 조건으로 사용합니다.

### 재연결
연결이 일정 시간 유지되면 대기 시간을 초기화하고, 아니면 지수적으로 늘립니다. 기본 대기 범위는0.5~2초이며 최대25% 지터가 더해집니다. CCTV-01D의 첫 장애 시험7.108초가 복구5초 목표에 미달해 기본 상한을10→2초로 줄였고 최종3.577초를 관측했습니다. 명시한 사용자 설정은 유지합니다. 동시 연결 시도 수도 제한합니다(기본8개). 주기적인 재연결이나 시간 제한 종료는 플러그인에 넣지 않습니다. 시험 하네스의 실행 시간 제한과 Close/Open 반복은 TestHost 전용입니다.

### 과부하 처리
재연결 상한2초는 복구 대기를 줄이지만 실패가 빨리 반환되는 꺼진 카메라에 약2초 대기 뒤 재시도하는 부하를 만듭니다. 연결·읽기 기한과 지터는 별도로 더해집니다. 서버의 동시 연결 제한이 작으면 최대 대기와 동시 연결 시도 수를 조정합니다.

패킷 큐가 상한을 넘으면 큐를 비우고 다음 키프레임까지 건너뜁니다. 참조 프레임이 빠진 깨진 화면을 내보내지 않기 위해서입니다. 이때의 손실은 `PacketsDropped` 통계로 확인할 수 있습니다.

### 하드웨어 디코딩 V1은 시스템 메모리를 거칩니다
디코딩 결과를 시스템 메모리로 내려받아 업로드합니다. GPU 간 직접 공유는 D3D12와 Vulkan에 각각 별도 구현이 필요해 V1에서 제외했습니다. 하드웨어 장치 컨텍스트는 채널끼리 공유하며 기본 HW 슬롯 상한은 프로세스 내4개, 나머지는 소프트웨어(채널당 FFmpeg 스레드 설정2)입니다. 슬롯은 디코더 시도 전 예약하고 전체 후보 실패 또는 연결 정리에서 반환합니다. CCTV-01D에서 Linux nullrhi CUDA4/SW12 및 video 라이브러리 누락 시 SW16Playing을 확인했습니다. 임의 GPU 장치 오류의 모든 회수 경로는 미검증입니다.

하드웨어 형식 협상에서 요구 형식이 없어지면 실제 기본 형식을 선택하고 실패 신호·DecoderName 통계를 함께 갱신합니다. 첫 키프레임 전에는 현재 소프트웨어 디코더를 계속 사용해 재연결 반복을 막고, 키프레임 수신 후에는 기존 세션 정리를 통해 소프트웨어로 다시 엽니다. 하드웨어 실패를 정상 CUDA 사용으로 표시하지 않습니다.

Linux NVDEC에는 libnvcuvid 노출이 필요하며 로컬 컨테이너는 `NVIDIA_DRIVER_CAPABILITIES=all`에서 확인했습니다. Vulkan RHI 초기화는 플러그인 로드 전 엔진 단계입니다. 기존 dzn/lavapipe와 엔진 제공 프로파일 우회 시험도 실패해 렌더링은 ENV_BLOCKED입니다. 우회 옵션은 운영 설정이 아닙니다. README의 드라이버 점검과 `TestHost/Scripts/linux_server_check.sh`로 실제 서버의 Vulkan/NVDEC/표시를 별도로 확인합니다. 해당 스크립트는 로컬 SW 모드만 실제 실행했습니다.

### 크기 조절
렌더 타깃은 표시 크기에 맞춰 줄어들고 원본보다 커지지 않습니다. 원본 변경은 즉시 반영하고, 표시 크기 10% 이상 변화는 0.25초 대기 후 반영합니다. 출력 폭·높이가 모두 원본의 절반 이하이면 디코딩 스레드에서 업로드 전에 축소합니다. 나머지 렌더 타깃 축소는 4탭 샘플링으로 보완합니다.

`SubUrl`을 지정하면 표시 폭이 기본 960px 미만인 상태 또는 그 이상인 상태가 2초 유지될 때 자동 전환합니다. 새 세션의 첫 프레임까지 기존 세션을 유지합니다. `SetUseSubStream` 호출은 해당 Open 수명 동안 수동 선택을 유지합니다. 전환 대기 중 새 주소가 실패하면 기존 영상과 새 세션의 장애 재연결을 유지하며 별도 전환 시간 제한은 두지 않습니다.

### 수명과 메타데이터

CCTV-01E부터 코덱·프레임 참조가 모두 끝나 캐시 참조만 남은 HW 장치는 읽기 스레드의 연결 정리에서 해제합니다. 사용 중인 참조와 장치 생성 실패 기록은 보존합니다. 다시 열 때 장치 초기화 비용이 다시 들 수 있으며 Close/Open·fault 최종 회귀로 확인합니다. GPU 프로세스 계정값은 드라이버를 포함하므로 `PlaneTextureRebuilds`와 RHI 텍스처 할당량을 별도로 기록합니다.

렌더 명령은 프레임·YUV 렌더러·진행 수 카운터의 공유 참조를 보관하며 `UDTCctvStream`을 캡처하지 않습니다. 텍스처의 render resource는 UE의 비동기 해제 fence로 보호됩니다. 실제 렌더 대기 중 GC와 반복 크기 변경은 별도 UE 검증이 필요합니다.

세션 닫기는 stop 신호·인터럽트·큐 Abort를 요청한 뒤 지연 해제 목록으로 넘깁니다. 읽기 스레드는 디코딩 스레드 종료 후 코덱·스케일러·입력을 정리합니다. 모듈 종료에서는 남은 세션을 기다린 뒤 공유 HW 장치와 FFmpeg 네트워크를 정리합니다. 읽기 스레드 생성 실패도 완료 상태로 남겨 회수할 수 있게 했습니다.

`CloseAllStreams`는 상태 콜백을 호출하기 전에 닫을 목록을 별도로 강하게 참조하고 관리 목록을 비웁니다. 콜백에서 목록을 바꾸거나 GC를 요청해도 순회 대상의 수명을 유지하며, 콜백이 새로 연 스트림을 기존 순회가 지우지 않게 합니다. 콜백 재진입의 실제 UE 검증은 남아 있습니다.
